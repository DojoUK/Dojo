# Audit notes: Dojo at `a84b04a` (8 October 2026)

> First audit of this repo under the risk-weighted QA method. Author: Matt Wood.
> Written against `main` at `a84b04a` (merge of PR #58, 28 August 2026), the GitHub
> repo state on 8 October 2026 (open PRs #52, #57, #59, #61; issues #11, #23, #24, #60, #62),
> and a run of the test suite inside the Compose stack. Every figure here can be
> regenerated from the repo; where one is wrong, that is the feedback wanted.

## What it is

A Django 6 / MySQL 8 / HTMX monolith: an open source, multi-tenant club management
platform (members, guardians, classes, attendance, invoicing, Stripe payments and
subscriptions, documents with canvas e-signature, progression, inventory). AGPL-3.0,
self-hosted by Docker Compose today, with a hosted SaaS (Dojo Cloud) planned.

- **Size.** 8 apps, 34 models, 143 routes, about 8,800 lines of Python and 7,700 lines of
  templates. 116 commits between 20 June and 28 August 2026, 51 of them on one day.
- **Access model.** Everything hangs off `Organisation`. Staff log in with Django auth and
  reach an organisation through three mixins in `dojo/mixins.py`: `OrgMixin` (any staff
  member of the org in the URL), `OrgAdminMixin` (role `org_admin`; superusers bypass) and
  `ClassCoachMixin` (coach assigned to the class; admins bypass). 93 view classes use the
  admin mixin, 6 the org mixin, 3 the coach mixin. There is **no database-level
  isolation**: every query adds `organisation=self.org` by hand, so one missed filter is a
  cross-tenant read or write with no error.
- **Outsiders.** Members never log in. Each has a 32-byte `secrets.token_urlsafe` bearer
  token in the URL (`/p/<token>/`) that opens the portal, the data export, Stripe
  Checkout, subscription sign-up and the Stripe billing portal (6 views). `/join/<slug>/`
  is a public application form with a drawn signature. `/stripe/webhook/` is CSRF-exempt
  and signature-verified.
- **Money.** `billing/calculator.py` computes an invoice from a policy (flat or
  per-session with a multi-class discount), member discounts and a family-group
  percentage, floored at zero. The bulk run (`BulkInvoiceView`) guards on `period` label
  per member and accepts per-row float overrides. Stripe handles cards; the webhook
  records payments and mirrors subscription invoices. `Invoice.status` and `Payment` rows
  are two separate sources of truth for "paid".
- **Personal data.** Children's dates of birth, medical information, guardian contacts,
  addresses, staff DBS numbers, drawn signatures (base64 PNG on the application row),
  signed waiver PDFs and uploaded documents under `media/`.
- **Jobs.** Four management commands meant for cron: `enforce_retention` (anonymises
  members archived more than 3 years, deleting guardians and notes), `purge_stale_applications`,
  `rotate_stale_portal_tokens` (180 days, emails the new link) and `send_overdue_reminders`.
  Plus `seed_demo --flush`, reachable from the UI for demo-flagged orgs, which deletes
  every row of every model and every non-superuser user.
- **Deploy.** `docker compose up`: the container generates and persists `SECRET_KEY`,
  waits for MySQL and runs `migrate` on every boot. `runserver --insecure` is the
  production server in the documented setup. `DEBUG` defaults to `True` and
  `SELF_HOSTING.md` tells operators to leave it so because `collectstatic` is not wired.

## Tier

**Tier 1.** It trips all three triggers in the method: customer-facing (portal, signup),
money (Stripe, invoices) and personal data (minors' medical and contact data). The
coverage destination is 80 percent with the money modules at 100 percent. The owner of the
project and of this strategy are the same person, so, as with the Vanaways BI platform,
this document decides rather than proposes.

## Testing currently in place

- **Zero tests.** One `documents/tests.py` containing Django's placeholder comment.
  `manage.py test` inside the stack reports `Found 0 test(s)`.
- **The runner cannot run.** With the Compose defaults the app user cannot create the
  test database. The reviewer of PR #61 hit `Access denied for user 'dojo_user'@'%' to
  database 'test_dojo'` and granted rights by hand. On this machine the app user could not
  connect at all, because the MySQL volume was created under different credentials from
  the current `.env` (the same class of fault: the test environment is not reproducible).
- **Eleven tests exist in a pull request.** PR #61 (31 August, open) adds
  `billing/tests.py` covering the webhook: both Stripe payload shapes, redelivery,
  the method value and the configuration guards. Six of them fail against `main`.
- **No CI, no `.github/` at all**, no branch protection or rulesets on `main`, no PR
  template, no linter, no formatter, no pre-commit hooks, no Dependabot, no secret
  scanning. 15 PRs, none with a review (solo maintainer).
- **Dependencies are unpinned.** `requirements.txt` lists nine names with no versions.
  The image built today resolves Django 6.0.7 and `stripe` 15.3.1; the PR #61 author ran
  Django 6.1 and `stripe` 15.6.0 a month ago. Issue #60 is exactly this failure class:
  the Stripe SDK moved a field and subscription payments were silently dropped.
- **Migrations** are applied automatically on boot (compliant with the SOP's §6 rule),
  but nothing checks for unapplied model changes or conflicting migration graphs. A
  duplicate `0010` pair with a merge migration shows a conflict has already happened once.
- **Audit logging** is registered for 20 models, but the in-app audit view filters to 7
  content types, so billing, documents, inventory and progression changes are logged and
  not visible.

## The findings that shape the plan

1. **Personal documents are served to anyone with the path.** `dojo/urls.py` mounts
   `static(MEDIA_URL, document_root=MEDIA_ROOT)`, which Django activates when
   `DEBUG=True`, and the documented deployment runs with `DEBUG=True`. Signed waivers land
   at `media/signed_waivers/YYYY/MM/<Name>_<Template>.pdf` (spaces to underscores),
   uploaded documents under `media/documents/YYYY/MM/`. No authentication. On an
   internet-facing instance this is a child's signed medical waiver one guessable URL away.
   The authenticated download views exist (`DocumentDownloadView`, `SignedWaiverDownloadView`)
   and are the right door; the open door beside them is the defect.
2. **The boundary is 93 hand-written filters.** Every one read for this audit was correct
   except two: `AddCoachView` resolves `User` by primary key with no organisation
   membership check, so an org admin can attach any user in the database to their class
   (the stranger still cannot log in to that org, but their name appears in it and the
   cross-tenant reference exists); and `ReseedDemoView` runs `seed_demo --flush`, which
   wipes **every** organisation, not the demo one. Both are harmless with one tenant and
   serious with two, which is the SaaS plan.
3. **Money has two sources of truth and float in the path.** `MarkPaidView` sets
   `status='paid'` without a `Payment` row, so revenue (a sum of payments) and outstanding
   (a sum of unpaid invoices) can disagree for the same invoice. `Invoice.Status.OVERDUE`
   is never assigned, so the overdue filter on the invoice list always returns nothing
   while `is_overdue` is computed on the fly. `RecordPaymentView`, the bulk-run overrides,
   `VariantCreateView` and `VariantEditView` pass `float` into `DecimalField`s.
4. **Email recipient resolution is copied eight times with two different rules.** Invoices,
   reminders and cancellations prefer a guardian when any guardian exists; welcome, announcements,
   bulk email and the waitlist notice prefer the member's own address. A child with their
   own email and a guardian gets invoices addressed to the parent and the welcome to the
   child. Every one of those sites swallows exceptions with `except Exception: pass`.
5. **The destructive jobs have no tests and no clock injection.** `anonymise()` deletes
   guardians and notes and is irreversible. The retention command computes its cutoff from
   `timezone.now()` inline. A wrong cutoff is either destroyed data or unlawfully kept data,
   and nothing today would notice either.
6. **The upstream contract is the Stripe SDK's default API version.** Nothing sets
   `stripe.api_version`, so the payload shape the webhook parses is whichever version the
   unpinned SDK defaults to on the day the image is built.

## What this repo adds to the method

- **A Django/MySQL variant.** The five Vanaways strategies are TypeScript on Supabase or
  Python on Postgres. Here the natural layers are Django `TestCase` against a throwaway
  MySQL service, the test client for the boundary suite, `locmem` email outbox for the
  send rule, and `freezegun` or an injected clock for the jobs.
- **Test-database provisioning as a Phase 0 item.** On Supabase the throwaway stack is
  `supabase start`; here it is a MySQL grant. It belongs in the Compose file, not a
  reviewer's shell history.
- **Open source governance.** No Confluence, no Jira. The strategy lives in the repo under
  `docs/qa-strategy/`, the backlog is GitHub issues labelled `qa-strategy` with one
  milestone per phase, and the stub at the root points here. Forked PRs from strangers
  mean CI must carry no secrets and the Stripe test-mode journey runs on a schedule, never
  on a pull request.
